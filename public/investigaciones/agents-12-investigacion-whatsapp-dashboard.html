AGENTS-12 - Investigacion de solucion para WhatsApp en dashboard

Fecha: 2026-05-16. Repositorio de salida: infra-specs. Documento para revision humana antes de ejecutar cambios en infraestructura o producto.

Resumen ejecutivo

La integracion es factible si el dashboard usa la WhatsApp Business Platform como canal servidor a servidor y los usuarios internos chatean desde la aplicacion autenticada, no desde WhatsApp Web ni desde sus telefonos personales. El numero del lead no puede desaparecer de todo el sistema porque Meta, el backend y el canal de mensajeria necesitan un identificador direccionable para enviar mensajes. Lo que si es factible es que el numero no se muestre ni viaje al frontend, que se almacene cifrado, que se use solo desde un servicio backend con permisos controlados y que cada acceso quede auditado.

Recomendacion principal: construir un modulo propio sobre Meta Cloud API para el MVP si el objetivo central es proteger leads dentro del dashboard. Usar un BSP como Twilio, 360dialog, Gupshup o un inbox comercial solo si se prioriza velocidad de salida sobre control fino de datos, UI y costos.

La solucion no debe prometer proteccion absoluta contra exfiltracion: un agente puede pedir el numero al cliente dentro del chat, el cliente puede escribirlo en un mensaje, o un screenshot puede capturar datos visibles. El alcance real debe ser reducir la exposicion del numero en UI, API, exports, logs y permisos, mas controles de monitoreo y auditoria para detectar abuso.

Contexto y objetivo

El CEO solicita que los usuarios del dashboard puedan iniciar sesion y conversar con clientes dentro del proyecto por WhatsApp, sin ver el numero telefonico de los leads para reducir el riesgo de que se los lleven fuera de la plataforma.

El repo disponible para este ticket es infra-specs; no se incluyo el codigo del dashboard dash admins en este workspace. Por eso este documento separa hechos verificados, inferencias y recomendaciones, y deja como decision pendiente revisar el repo real del dashboard antes de estimar esfuerzo final.

Objetivo de proteccion No exponer el telefono del cliente al agente interno salvo roles explicitamente aprobados.

Alcance, no alcance y supuestos

Alcance

  • Evaluar opciones tecnicas para integrar WhatsApp al dashboard.
  • Definir arquitectura objetivo para chat, webhooks, almacenamiento, permisos y auditoria.
  • Proponer plan de implementacion, validaciones, riesgos, rollback y criterios de aceptacion.
  • Definir controles para que el telefono del lead no sea visible en la UI ni en respuestas API normales.

No alcance

  • No se implementa codigo del dashboard en este ticket.
  • No se abren cuentas de Meta, WABA, Twilio u otros proveedores.
  • No se aprueban plantillas, politica legal, terminos de privacidad ni contratos de proveedor.
  • No se garantiza que un agente no pueda obtener el numero si el cliente lo escribe voluntariamente en el chat.

Supuestos

  • El dashboard ya tiene autenticacion, usuarios internos y algun modelo de proyecto, lead o cliente.
  • Los leads ya tienen telefonos recolectados por formularios, ads o canales comerciales con consentimiento revisable.
  • La empresa esta dispuesta a usar un numero WhatsApp Business propiedad de la empresa, no el numero personal de cada agente.
  • La primera version puede iniciar con mensajes entrantes o con plantillas aprobadas para mensajes salientes fuera de la ventana de 24 horas.

Hechos verificados, inferencias y recomendaciones

Tipo Punto Implicacion
Verificado WhatsApp Business Platform esta orientada a negocios medianos o grandes que comunican a escala mediante acceso programatico. Encaja mejor que la Business App para un dashboard multiusuario y controlado por backend.
Verificado Meta documenta APIs oficiales para enviar y recibir mensajes, Business Management API, Flows y Embedded Signup. La integracion debe ser por API oficial y webhooks, no por automatizacion de WhatsApp Web.
Verificado Los mensajes se cobran por mensaje entregado segun categoria y mercado; los mensajes de servicio dentro de ventana de atencion son gratuitos, y la ventana de 24 horas se abre o reinicia con cada mensaje del usuario. La UI debe mostrar si la conversacion esta dentro de ventana libre o si se necesita plantilla aprobada.
Verificado La politica de WhatsApp exige opt-in, respetar opt-out, perfil de negocio correcto, privacidad, y limita mensajes fuera de la ventana de 24 horas a Message Templates aprobados. El producto necesita registrar consentimiento y bloquear envios no permitidos.
Inferido El objetivo de ocultar numeros se resuelve mejor en el backend y el modelo de permisos, no en WhatsApp mismo. El frontend no debe recibir phone_e164, wa_id crudo ni campos equivalentes salvo rol privilegiado.
Recomendado Usar un servicio interno whatsapp-service que sea el unico componente con token Meta y capacidad de descifrar telefonos. Reduce superficie de fuga y simplifica auditoria, rotacion de secretos y rate limiting.

Arquitectura propuesta

La arquitectura objetivo separa la experiencia de agente de los datos sensibles. El dashboard opera con identificadores internos de conversacion y lead; solo un servicio backend tiene acceso al token de Meta y al telefono descifrado. 

Cliente WhatsApp
  <-> WhatsApp Business Platform / Cloud API
       <- webhooks HTTPS firmados -> whatsapp-service
       <- REST interno / eventos -> API del dashboard
       <- JSON sin telefono -> frontend dash admins

Datos sensibles:
  - phone_e164_ciphertext: cifrado con KMS/Vault
  - phone_lookup_hash: HMAC para deduplicar/buscar sin revelar
  - phone_last4: opcional y solo visible a roles aprobados
  - wa_contact_id / bsuid / conversation_id: identificadores operativos no mostrados como telefono

Componentes

Componente Responsabilidad Datos sensibles
whatsapp-service Enviar mensajes, recibir webhooks, validar firma, manejar retries, mapear conversaciones, aplicar ventana de 24 horas. Si. Token Meta, telefono cifrado/descifrado en memoria, ids de WABA y phone number.
API dashboard Autorizacion por proyecto, endpoints para UI, busqueda de conversaciones, asignacion, notas y auditoria. No debe exponer telefono crudo a clientes normales.
Frontend dashboard Inbox por proyecto, lista de conversaciones, composer, template picker, historial y estados. No recibe telefono. Muestra nombre, alias, fuente, proyecto y estado.
Base de datos Persistir cuentas WABA, conversaciones, mensajes, eventos webhook, templates, auditoria y consentimientos. Si. Requiere cifrado, roles DB y mascaramiento en dumps.
Cola/event bus Procesar webhooks y envios de forma asincrona e idempotente. Debe transportar payload minimo o cifrado; no logs con telefono.

Reglas de UI

  • La lista de conversaciones muestra nombre, proyecto, ultima actividad, estado, asignado y etiquetas; no muestra telefono.
  • El detalle de conversacion no renderiza telefono aunque exista en el payload de proveedor.
  • Fuera de la ventana de 24 horas, el composer libre se bloquea y se muestra selector de template aprobado.
  • La descarga/exportacion de conversaciones queda deshabilitada para agentes o entrega versiones sin telefono.
  • Un modo estricto puede redactar patrones de telefonos escritos dentro del cuerpo de mensajes entrantes antes de mostrarlos a agentes.

Controles para evitar fuga de leads

Control Implementacion sugerida Limitacion residual
Mascaramiento de telefono El backend nunca serializa el telefono para roles agente. Solo roles como admin compliance pueden ver ultimos 4 digitos o telefono completo con justificacion. No evita screenshots de otros datos ni que el cliente escriba su numero.
Cifrado de datos Telefono y wa_id cifrados en reposo; hash HMAC para deduplicacion; llaves en KMS/Vault; rotacion planificada. El servicio de envio debe descifrar en memoria.
RBAC por proyecto El agente solo ve conversaciones asignadas o de proyectos autorizados; denies por defecto. Requiere que el modelo de proyectos actual este bien definido.
Auditoria Registrar lectura de conversacion, envio, asignacion, cambio de estado, export, intento denegado y acceso a dato sensible. La auditoria disuade y detecta, pero no elimina abuso humano.
DLP basico en mensajes Detectar E.164, emails y patrones de telefono en cuerpos de mensaje; mostrar redaccion para agentes o marcar riesgo. Puede generar falsos positivos y afectar conversacion comercial.
Sin WhatsApp Web Prohibir QR compartidos, sesiones web y librerias no oficiales. Todo envio pasa por backend. Necesita capacitacion y politica interna.
Watermark y anti-copy Watermark con usuario en la vista, rate limit de copy/export, bloqueo de select/copy solo si no afecta usabilidad. No es seguridad fuerte; ayuda como friccion y trazabilidad.

Costos y operacion

Meta cobra por mensaje entregado segun mercado y categoria. La pagina oficial de pricing indica cuatro categorias: marketing, utility, authentication y service. Los mensajes de service no tienen cargo dentro de la ventana de 24 horas abierta por mensajes del usuario; tambien se documenta una ventana gratis de 72 horas cuando el usuario llega desde ciertos entry points como Click to WhatsApp Ads o Facebook Page CTA.

Partida Impacto esperado Como controlarlo
Mensajes Meta Variable por pais, categoria y volumen. Marketing suele ser mas caro que service/utility. Dashboard de gasto por proyecto, categoria, template y agente; alertas por presupuesto.
BSP o Twilio Fee adicional por mensaje, sender o asiento, segun proveedor. Comparar TCO a 6 y 12 meses contra Cloud API directa.
Infraestructura Webhook service, cola, DB, almacenamiento de media, logs, monitoreo. Retencion limitada, compresion, lifecycle para media y logs.
Operacion Meta Aprobacion de templates, salud de WABA, calidad, opt-outs, rate limits y errores. Runbook de soporte, alertas y owner operativo claro.

Plan de implementacion

  1. Descubrimiento en dash admins. Revisar stack, auth, RBAC, modelo de proyecto/lead, permisos actuales, donde se muestra telefono, exports, logs y APIs existentes.
  2. Aprobacion de producto y legal. Confirmar paises, casos de uso, politica de opt-in, privacidad, retencion, roles que podran ver telefono y si habra redaccion de mensajes.
  3. Seleccion de proveedor. Decidir entre Meta Cloud API directa o BSP. Para requisito de ocultamiento fuerte, iniciar con Cloud API directa salvo que haya restriccion operativa.
  4. Setup de Meta. Crear o validar Meta Business Account, WABA, numero, Business Profile, app, permisos, System User token, webhook verification token y App Secret.
  5. Backend base. Implementar whatsapp-service, validacion de webhooks, cola, idempotencia, envio de texto, persistencia de eventos y estados de delivery.
  6. Modelo seguro de contactos. Migrar o guardar telefonos con cifrado, hash HMAC y contrato API que nunca devuelva telefono crudo para agentes.
  7. UI de agente. Inbox por proyecto, conversacion, composer, selector de templates, asignacion y estados. Confirmar por inspeccion de red que no se entrega telefono.
  8. Templates y consentimientos. Registrar opt-in, templates por categoria, aprobaciones y reglas para bloquear salidas fuera de ventana.
  9. Observabilidad y auditoria. Metricas, logs sin PII, trazas por message id, alertas de errores, gasto y eventos de acceso sensible.
  10. Piloto controlado. Activar con un proyecto, pocos agentes y numero dedicado. Medir tiempos, errores, gasto, feedback y eventos de fuga.
  11. Rollout gradual. Expandir por proyecto, con capacitacion y politicas internas sobre no pedir datos personales fuera de la plataforma.

Riesgos y mitigaciones

Riesgo Severidad Mitigacion Rollback
Exposicion accidental de telefono en API, logs o exports. Alta Tests de contrato, redaccion en serializers, logs estructurados sin PII, revisiones de seguridad. Desactivar endpoints afectados, rotar llaves, revocar exports, investigar auditoria.
Uso de mensajes fuera de politica o sin opt-in. Alta Modelo de consentimiento obligatorio, bloqueo de mensajes fuera de ventana y template approval. Pausar envios salientes, revisar templates, volver a canal manual aprobado.
Cuenta WABA restringida por calidad, spam o datos incorrectos. Alta Monitorear calidad, opt-outs, reportes, volumen y contenido. Mantener perfil de negocio exacto. Desactivar campanas, apelar en Meta, usar canal alterno aprobado para soporte critico.
Webhook caido o lento. Media Responder 200 rapido, procesar asincrono, cola con retries, alertas de latencia y error rate. Activar modo degradado: solo lectura, reintentos manuales y pausa de salientes si hay desorden de estado.
Agente intenta sacar al lead por texto. Media Auditoria, DLP basico, politicas internas, revision de conversaciones, alertas por patrones de telefono. Suspender usuario, bloquear conversacion, escalar a compliance.
Proveedor elegido limita masking o exporta telefono. Media Prueba de concepto con inspeccion de API/UI/export antes de contrato anual. Migrar a Meta Cloud API directa o proveedor con controles adecuados.

Validaciones y criterios de aceptacion

Validaciones tecnicas

  • Un agente autenticado puede ver y responder una conversacion asignada sin que el payload de red incluya telefono crudo.
  • Un agente sin permiso de proyecto recibe 403 al intentar listar o abrir conversaciones de otro proyecto.
  • El webhook valida firma, deduplica eventos y persiste mensajes entrantes y estados sin duplicados.
  • El composer libre se bloquea automaticamente cuando service_window_expires_at esta vencido.
  • El envio con template fuera de ventana usa solo templates aprobados y registra categoria/costo estimado.
  • Los logs de aplicacion, cola y errores no contienen phone_e164, wa_id crudo ni token de proveedor.
  • Los mensajes, lecturas, exports e intentos denegados generan audit_events.

Criterios de aceptacion de negocio

  • Los agentes pueden operar desde el dashboard sin usar telefono personal ni WhatsApp Web.
  • El cliente recibe mensajes desde el perfil oficial del negocio.
  • Sales Ops puede asignar conversaciones por proyecto y medir SLA de respuesta.
  • Compliance puede auditar quien vio o respondio cada conversacion.
  • Producto confirma que el numero del lead no aparece en UI, exports normales, notificaciones ni respuestas API de agente.

Plan de rollback

  1. Deshabilitar feature flag de WhatsApp en el dashboard por proyecto o globalmente.
  2. Pausar envios salientes desde whatsapp-service y conservar solo ingestion de webhooks si es necesario para no perder mensajes.
  3. Revocar o rotar token de proveedor si hubo exposicion de secreto.
  4. Desuscribir webhook o apuntarlo a endpoint de mantenimiento si el procesamiento causa incidentes.
  5. Volver al canal operativo anterior aprobado por negocio, dejando claro que ese canal puede no cumplir el mismo nivel de masking.
  6. Preservar transcripts y auditoria para investigacion, aplicando retencion y controles de privacidad.

Preguntas abiertas

  • Que stack usa dash admins y como modela usuarios, proyectos, leads y permisos?
  • El telefono del lead ya esta oculto en alguna parte o hoy aparece en listados, detalle, exports y APIs?
  • Se usara un numero WhatsApp nuevo o un numero existente que podria requerir migracion o coexistencia?
  • En que paises estan los leads? Esto afecta tarifas, plantillas, compliance y horarios de contacto.
  • Que roles, si alguno, pueden ver el numero completo para soporte o compliance?
  • El caso inicial es solo responder mensajes entrantes o tambien iniciar contacto proactivo?
  • Se necesita IA/bot o solamente agentes humanos? Si hay IA, revisar politicas especificas antes de disenar el flujo.
  • Que retencion de transcripts, media y auditoria exige negocio/legal?

Decision recomendada

Aprobar una fase 0 de descubrimiento sobre el repo dash admins y una fase 1 de MVP con Meta Cloud API directa, numero de negocio dedicado, webhook backend, almacenamiento cifrado, UI de inbox por proyecto y contrato API sin telefono para agentes. La aprobacion debe incluir que el objetivo es ocultar y controlar exposicion interna, no eliminar completamente el telefono de todos los sistemas.

Si negocio necesita piloto en menos tiempo que el desarrollo propio, evaluar Twilio Conversations o un BSP con una prueba de concepto obligatoria: inspeccionar UI, APIs, webhooks, exports, roles y logs para confirmar que el telefono del cliente no se expone a agentes.
